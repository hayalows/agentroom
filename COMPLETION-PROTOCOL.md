# Bank completion and review-first work policy

This replaces the previous open-claim limit and per-bank lead confirmation step for the Ghana banking goal. It does not change MODEL-SPEC.md, source requirements, independent review, ownership, or the existing financial quality bar.

## Priorities at each sync
Finish the current small milestone and push it. Read latest main, all boards, current claims, reviews and help requests. Read the supervisor queue (node scripts/supervisor.mjs --json or the latest Room status workflow summary).
1. ACK and act on addressed messages; verify delivered assistance.
2. Close your own verified submissions; repair real blocking findings, or explicitly report blockers. If you are the lead, resolve escalated review disputes.
3. Offer needed peer assistance and review another owner's eligible bank before claiming additional work. A reviewer does not claim a bank and may not approve their own model. Post REVIEW-START <slug> on your own board before reviewing; sync first to avoid duplicate effort. Another reviewer may take over a quiet review after 20 minutes; never overwrite another review.
4. Continue existing active work. If no repair, closure, peer review or assistance needs you and capacity exists, claim an unclaimed bank. When waiting for others, work on useful eligible tasks instead of ending the session.

Up to six unfinished assignments combined (active, repair, submitted-waiting). This is a queue, not permission to work on six files at once. Work on one bank milestone at a time, and push before switching. Reviews and bounded help do not count as bank claims. A ready review remains the suggested priority, but available agents can reserve and then work on another bank when waiting for responses or evidence. Do not hoard claims. The dashboard separately tracks active and submitted-waiting counts, with a combined cap of six. These rules are advisory, not a server-side lock.

## Explicit pause and handoff
The human-authorized goal availability.json lists explicit pauses and task-specific handoff offers. A quiet timestamp alone is never a pause. The named owner can post a dated RESUME on their own board; the scheduler does not infer a return from an expected reset time. A volunteer accepting an offered handoff must sync, confirm the offer and that no steward exists, atomically update the existing claim with `steward: <your-id>` (retain `agent: <original-author>` and all existing progress), push before editing model files, and post an acceptance on their own board. GitHub-only workers must use the current blob SHA to avoid concurrent overwrites. The steward becomes the sole writer for that claim/package, accountable for answering reviews and closing after valid independent PASS. The returning original author must not edit the transferred package unless the steward and human explicitly return it. Preserve all prior review files and original-author identity in filenames; a steward may not independently review/approve their own work. Existing blockers cannot disappear on transfer. If an old reviewer is explicitly paused, use the evidence-based substitute-review procedure below; no automatic override of a blocking review. Completed models are excluded from handoff. Only named offers in availability.json authorize handoffs. The human has authorized the specific additional offers listed there. A paused steward can be replaced only when the named replaceSteward matches the current paused worker; retain previousStewards, which disqualifies former builders from reviewing that package. A returning prior steward must not edit unless explicitly returned. Released assignments may be reclaimed with a separate <slug>-takeover.md claim, retaining the released file; never create a competing active claim. Do not impersonate or edit another board.

## Model closure
A complete bank needs the core gate, a distinct registered reviewer's current-version PASS, no unresolved CHANGES/BLOCK verdict and an owner claim marked done. An ordinary clean PASS no longer needs a separate per-bank lead confirmation. The read-only supervisor computes accepted from these independent records; its state.json contains the owner, review file, reviewer, review SHA-256, package and macro fingerprints. Nothing automatically changes bank files or claims. This is evidence of completion of the model specification, not regulatory compliance, audited accuracy, or investment advice.

A current-version PASS must include these exact labels within the newest dated verdict section:
```
Verdict: PASS
Package SHA-256 fingerprint: <64 hex from task.gate.fingerprint>
Macro SHA-256 fingerprint: <64 hex from task.gate.macroFingerprint>
```
State the actual source checks, arithmetic/replay, remaining limitations and reviewed version. Never copy hashes from an old review to bless new content. Mixed historical PASS / forecast CHANGES counts as CHANGES. Supplemental evidence is not a full review. Old PASS without exact current fingerprints must be revalidated by an independent reviewer. After PASS, author or authorized steward checks current supervisor gate and latest review(s), responds to limitations, then marks only their own or explicitly stewarded claim done. If source/model issues arise, reopen and repair rather than conceal them. An accepted model becomes unaccepted if current evidence changes.

For revisions after CHANGES, keep old review evidence, address every finding and set your claim status to needs-review with two extra fields `review_revision: <current package SHA-256>` and `review_macro: <current macro SHA-256>`. Post a message to the reviewer with the changed files and what was fixed. This routes the previous reviewer back to the revision; it does not erase their blocking verdict. If tools cannot compute the fingerprints, ask a peer or use the Room status snapshot. The reviewer appends a dated verdict, without editing prior review sections. If a third review round is still blocking, the lead resolves the dispute or asks the human; do not treat unresolved failures as PASS. All independent evidence requirements remain.

The lead remains responsible for disputed cases, shared methodology, and final sector-level acceptance. The rollup, comparison and final QA tasks become eligible when all bank models meet their acceptance gates. No automatic model calls or chat restarts are added. Agents see these instructions and new messages at their next synchronization.

## Reduced-team closeout: paused reviewer substitution
When an earlier reviewer is explicitly paused, and an owner has resubmitted a current exact package, a different independent reviewer may verify every original finding. A second distinct independent reviewer must verify the same finding-by-finding evidence and current package. Neither may be the original author, current steward, former steward, or paused blocking reviewer. This is not a waiver. Both must append exact current PASS verdicts in their own normal review files and include an exact line `Resolved review SHA-256: <hash of original blocked review file>` in the latest verdict section. Preserve the old review file unchanged. The two reviewers jointly record `review-resolutions/<slug>.json` with schema 1, packageFingerprint, macroFingerprint and a resolutions array; each entry has blockedReviewFile, blockedReviewHash, primaryReviewFile, primaryReviewHash, verificationReviewFile, verificationReviewHash, resolvedAt (UTC), findings (array of {finding,evidence}). All hashes are SHA-256 of current review text, as shown in supervisor peerReviews. Include EVERY original issue, not merely a summary. The supervisor accepts only exact current evidence, explicitly recorded pause predating resolution, and two independent PASS reviews with the matching acknowledgment. A later edit of package, macro or review invalidates resolution. Original reviewer can still re-review on return. No single reviewer can substitute themselves for another; unresolved or active reviewer disputes still go to lead/human. The automated gate validates record structure and binding, not truth of evidence. No resolution is created automatically.

Do not delay building other banks because a paused reviewer is unavailable. Use named handoffs, released claims, or bounded help. If only two independent participants remain available for a task that needs two substitute reviewers, retain the block and continue other work. Do not infer availability from time or consume additional usage without authorization.
